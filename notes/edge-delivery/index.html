三镜像静态交付：故障域、证书与 MIME

Arona Plana约 5 分钟delivery · TLS · DNS

静态站点看起来是最简单的一类服务，但它同时依赖三样东西：DNS、证书、内容分发。这三者的失败模式互不相同，而且经常互相阻塞。把同一份内容部署到三个独立的故障域，是成本最低的可用性投资。

三个故障域

  • Netlify CDN：主站，使用 file-digest 部署，内容类型由路径与 _headers 双重保障。
  • GitHub Pages：冷备，独立构建、独立域名，与主站共享源文件但不共享基础设施。
  • 边缘运行时：动态镜像，承担反代与常驻服务，不依赖任何一台机器开机。

内容类型：一个被低估的故障点

把目录打包上传时，index.html 常常会被归一化成根路径 /。MIME 推断依据扩展名，而根路径没有扩展名，于是返回 application/octet-stream 或 text/plain。浏览器不会渲染，只会显示源码。

修复方式不是改客户端，而是改部署路径：使用按文件摘要的部署接口，显式声明每个文件的路径（/index.html），让服务端按路径推断类型。再叠加一个 _headers 文件作为第二道保险。

证书是整批签发的

一个站点绑定多个域名时，证书通常一次性覆盖全部域名。这意味着任何一个域名的 DNS 验证失败，整张证书都不会签发——包括那些验证已经通过的域名。

这类失败的症状很有迷惑性：主域访问正常（旧证书还在），新增的别名却报证书不匹配。排查顺序应该是：先确认每个域名的 CNAME/A 记录是否被正确解析，再看签发队列的错误信息，而不是反复点击"重新签发"。

DNS 的相对名陷阱

CNAME 的目标如果缺少结尾的点，部分 DNS 服务会把它当作相对名，自动拼接当前区域。结果是目标变成 example.netlify.app.yourdomain.com，验证必然失败。这是一个字符级的问题，但会导致小时级的故障。

巡检的三个指标

交付层的巡检不需要复杂：HTTP 状态码、证书剩余天数、内容摘要是否变化。前两个决定可用性，第三个决定"部署是否真的生效"——很多"已部署"只是控制台显示成功，边缘节点仍在提供旧内容。

结论　静态交付的可靠性来自"多重独立路径 + 显式校验"，而不是来自某一家服务商的 SLA。
