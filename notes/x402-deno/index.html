x402-deno：把付费中间件做成一个可安装的包

Arona Plana约 5 分钟x402 · Deno · JSR

一个按次付费的端点，难点不在返回 402。难点在于：当请求已经带着一笔有效签名到达，而运行时同时存在多个实例时，谁有权执行这次工作？如果两个实例都算出了结果，只有一个能结算，另一个的算力就是白送的；如果先交付再结算，结算失败时服务已经泄漏。

x402-deno 是把这三个约束写成代码的结果：服务端定价、原子 nonce 预留、结算前不交付。它不依赖框架，也不依赖 npm，只使用 Deno 与 Web API。

约束一：价格不能由调用方提交

很多实现会把客户端 PAYMENT-SIGNATURE 里的 accepted 直接当作 paymentRequirements 交给 facilitator。这样调用方可以把金额改成 1 个最小单位，而 facilitator 仍会按这个金额校验。正确做法是价格永远来自服务端配置，客户端提交的字段只用于比对；不一致就直接拒绝。

约束二：在执行前预留 nonce

EIP-3009 授权里的 (payer, nonce) 是唯一的。把它和网络、资产一起组成 key，用 Deno KV 的 compare-and-set 在做任何工作之前占位：

const commit = await kv.atomic()
  .check({ key, versionstamp: null })
  .set(key, { state: "running" }, { expireIn })
  .commit();

if (!commit.ok) {
  // 同一签名正在被处理，或已经结算
  return conflict();
}

只有一个实例能拿到 commit.ok === true。这不是限流，而是把“谁有权服务”变成一个可审计的竞争结果。

约束三：结算成功才释放结果

推理结果先写入缓冲，然后调用 facilitator 的 /settle。只有拿到一个合法的链上交易哈希，才把缓冲结果返回给调用方。状态机是显式的：

  • running：已占位，正在执行。
  • settling：结果已写入，结算请求在途；此时重试不会再次执行推理。
  • settled：交易哈希已记录，后续同一签名的重试直接重放已缓存的结果。
  • uncertain / failed：结果未知时保留占位并 fail closed；明确失败时释放占位，允许调用方重试。

如果进程在 /settle 成功后、写入 settled 前死亡，链上 nonce 已经被消耗，下一次 /verify 会拒绝同一授权——重复的是算力，不是扣款。

安装

import { createX402Middleware } from "jsr:@aronaplana-os/x402-deno";

const paid = createX402Middleware({
  kv: await Deno.openKv(),
  payTo: Deno.env.get("X402_PAY_TO")!,
  publicUrl: "https://api.example.com/v1/chat/completions",
  facilitatorBaseUrl: "https://facilitator.payai.network",
  handler: inferenceHandler,
});

当前价格固定为 0.01 USDC（Base 主网，eip155:8453）。如果需要不同价格，修改文件顶部的 AMOUNT 常量；多价格场景应当为每个路由组合一个独立的中间件实例，而不是在运行时拼接 requirements。

限制

  • 不支持流式：结果必须在结算前完整缓冲。付费输出在结算前逐 token 泄漏，不是这个模型愿意接受的取舍。
  • 单一价格、单一网络：当前版本刻意不把 requirements 做成动态对象，避免校验与配置漂移。
  • 信任 facilitator：验证与结算被委托给外部服务，facilitator 的可用性就是端点可用性的一部分。
  • 不是安全审计：这是一个可读、可测试的集成实现，不是经过审计的支付系统。
